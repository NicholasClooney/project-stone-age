# 宠物记录实时刷新

## 根因

战斗和自动化状态推送会触发通用的 `rebuild()`，原先无论记录数据是否变化都会删除整个 `panel`，再创建窗口、按钮和滚动容器。`fetch_records(true)` 虽然不显示载入提示，响应返回后仍无条件调用同一重建路径。旧滚动恢复依赖延迟布局，连续推送可能不断替换刚恢复的节点；hover 和下拉菜单的节点也被销毁。

视图签名还直接保留排序数组的引用，后续修改会让“已绘制视图”跟着变化，无法可靠判断视图是否相同。

## 修复

打开的记录窗口使用独立增量同步路径。数据、载入状态和视图相同就跳过绘制；quiet 响应与当前数据相同也直接返回。签名使用深拷贝。数据有变化时先生成离树的控件描述，按位置和类型复用已有控件，只更新文字、提示、样式、选择和回调；主题覆盖精确同步，旧有但新描述没有的覆盖会显式移除，恢复默认继承，避免旧标签金色或旧行红色残留；结构变化才替换局部节点。窗口和实际的 `RecordsScroll` 留在场景中，滚动值在同步前后保持。页数、品种选项等回调随内容更新，避免保留旧数据。品种或本轮下拉菜单打开时延后同步，菜单关闭后渲染最新数据，不中断选择操作。

UI 仍通过 `world.session.pet_log()` / `hunt_queue()` 请求真实后端，未引入 UI 本地记录源。排队状态签名仍负责触发刷新，返回的数据没变化时不重绘。

## 验证

`pet_records_refresh_test` 使用真实 game、backend 和 session，连续开启并关闭真实战斗，验证抓到/放生页节点、非零滚动位置、页码、排序和数据更新。排队验证真实自动化队列事件刷新、无变化状态不重绘、非零滚动保持，以及从真实 session 读取当前练级宠物的最新等级。此外通过实际点击各标签、排序列、翻页和品种/本轮选项，检查新回调及高亮切换；复用行的红/绿样式变化和多余主题覆盖清理也有断言。现有 `pet_records_test`、`hunt_queue_records_test` 覆盖捕获/放生记录和真实 WebSocket 远程客户端。

这些都是 headless 测试，检查节点与状态，不能验证渲染像素。
