# Exact quest NPC lookup cost

The stage-two integration at9af2257, with the current main imported catalog cloned locally (297 source NPCs,2,791,432 bytes; SHA256 `0c0fbe8ccf0b8480528d5a8711f858aaba4a33b8200a501ae762b1b1c810b8f5`), exceeded the420-second water transaction budget. A temporary instrumented complete run took479.88s real,473.86s user CPU and3.35s system CPU. It made63,860 `active_npcs()` calls costing351.349s inclusive,9,495 navigation-key calls costing132.885s, and175 quest snapshots costing341.800s. These nested totals must not be added. Route pathfinding and legitimate-arrival movement checks were small; the guard battle took18ms. This is evidence of repeated projection/copy cost, not an assertion that host load caused a flaky test.

`active_npc(id)` uses the same ordered per-record projection as `active_npcs()`, including enabled-event branches, personal movement/hidden state, unspawned regional actors, TimeMan visuals, golden services, the jug shop and independent Charm services. It preserves first-active duplicate-ID behavior and fresh deep copies. `original_quests.npc_by_id()` still refreshes personal state before lookup. There is no shared mutable result cache, cross-profile cache or delayed invalidation.

`quest_catalog_lookup_test` retains the original full-array algorithm as an independent oracle. It checks every actual source and service ID, absent IDs, water disabled while adult gates remain, personal move/hide, regional birth, shared event12 event subsets, TimeMan visual changes, duplicate ordering and nested-return isolation between catalogs. Its same-catalog298-ID comparison initially measured1,790,759us for the original lookup versus11,364us for the single-record lookup. No task rule, reward/RNG operation, source catalog or save schema changes.

Temporary profiler wrappers and the one-off snapshot probe are removed from delivered code. The source/oracle-only dependency a60609a is included locally as an equivalent commit after9af2257. Subsequent navigation-key work and complete bounded suite verification are recorded separately.

## Navigation key projection

The second change retains Golden Bui's exact `[map_id]` result outside its protected maps, returning before reading the catalog. Wind retains its original four-field key, including personal NPC version, region and ordered eligibility. It uses `active_npcs_on_map()` to filter source records by their effective personal map before deep-copy projection. Public map 100, Munde 11107 and personally relocated NPCs remain candidates. Neither change caches mutable dictionaries or removes near-talk invalidation.

`quest_navigation_projection_test` compares both keys with independent copies of their original algorithms. It covers every actual catalog map, absent maps, independent services, public/Munde/wind/water maps, personal version and moved/hidden overrides. An actual source wind gate and six-floor walk establish legitimate arrival before checking near/far talk changes; the test does not grant arrival marks.

The baseline and optimized water runs retain 4,660 position reports, 9,495 navigation keys, 175 helper snapshots and 51 route path searches. Complete execution falls from 479.88s to 250.916s (248.832s user CPU, 1.465s system CPU), within the unchanged 420s budget. Navigation-key inclusive time falls from 132.885s to 4.166s: wind from 64.760s to 1.461s, Golden Bui from 63.959s to 0.015826s. Route/guard time falls from 254,745ms to 117,414ms; actual guard battle time remains 18ms. Remaining full catalog projections are measured rather than attributed to load. Timings include temporary profiler overhead; all profiler wrappers are removed from the delivered files.
