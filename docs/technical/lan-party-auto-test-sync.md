# Party automation test switch synchronization

The real WebSocket client in `lan_party_auto_test` waits for both server and local profile values before toggling quick battle on again. Those values can arrive before `party_panel._auto_battle_frame()` copies them into the checkbox. A programmatic assignment of `true` to an already-true checkbox emits no toggle signal, so the next server-setting assertion waits for a request the test never sent.

A diagnostic run reproduced this without changing test behavior. At engine tick 148044ms, switching off emitted `toggled(false)`. When the original off predicate succeeded, the checkbox was still `true`, while local and server settings were both `false`. Immediately assigning `true` produced no `toggled(true)` signal; all three values stayed unchanged. The run reached the original 300-second limit at 300.036s (167.226s user CPU, 2.842s system CPU). The prior full-suite sample likewise spent 1484 of 1675 main-thread samples in frame-delay sleep. This distinguishes asynchronous control synchronization from a product failure to apply the off setting, which both profiles had already applied.

The test now requires the checkbox to match each acknowledged setting before continuing: false after off, true after on. Existing server/local predicates, the 60-second condition deadline and the 300-second suite budget remain. There is no fixed sleep, product change or relaxed assertion. Diagnostic logging and timers are removed from delivered code.

With all probes removed, the complete suite passes with 0 failures and no script errors in 147.826s (143.161s user CPU, 2.352s system CPU), within its original 300s budget. The real client acknowledges off and on, presents compact battle, opens the battle view, returns to compact mode for the next battle, and closes it on both client and server. The successful run does not record individual signal timestamps; the precise 148044ms signal evidence belongs to the preceding diagnostic run.
